코드에서 위험을 찾는 기능을 만들면서, 결과를 어떤 근거로 보여줄지도 함께 설계했습니다.
아래는 2026년 10월 30일 비공개 저장소의 최신 main과 대조한 구현 구조와 그 선택의 이유입니다.

01. 요청 처리와 분석 실행을 나눴습니다

분석은 화면 요청보다 오래 걸리고, 사용자가 브라우저를 닫거나 같은 요청을 다시 보낼 수도 있습니다.
Next.js API는 인증·입력·권한을 확인해 작업을 준비하고, Vercel Workflow가 실제 분석을 이어 갑니다.
서버 코드는 Route → 입력 검증 → Service → Repository/RPC로 나눴습니다.

GitHub 수집용 Workflow가 고정 커밋의 파일을 모아 private Storage에 저장합니다.
준비된 입력으로 분석용 Workflow를 시작하면 규칙 분석·의존성 추출 → OSV 조회 → 자체 코드 분석 → 결과 저장 → Sandbox 정지 → 선택 AI 검토와 후보 저장 → 원본 정리 순서로 실행합니다.
파일 수집은 최대 8개, OSV 조회는 최대 4개 요청을 병렬로 처리합니다.
두 병렬 처리는 각각의 단계 안에서 이루어집니다.

입력·엔진·규칙·분석 설정 등의 조건이 같은 결과는 검증 후 캐시에서 재사용할 수 있습니다.
재사용 시에도 입력 준비와 현재 권한을 확인하며, OSV 조회 결과를 그대로 재사용하지 않습니다.
AI에 코드를 보낼 때는 비밀정보를 다시 점검하므로, 이전 정적 분석 결과만으로 AI 문맥을 만들지 않습니다.


작업 시작과 결과 저장의 기준

문제 구현 선택 얻은 동작
DB 저장과 외부 Workflow 시작을 하나의 트랜잭션으로 묶을 수 없음 실행 기록과 outbox를 함께 저장 시작 요청이 실패해도 재조정할 대상을 DB에 남김
같은 작업이 중복 전달될 수 있음 DB의 claim과 lease로 실행권 확인 현재 실행권을 얻은 작업이 단계를 진행
취소·권한 철회 이후 이전 응답이 도착할 수 있음 작업 generation과 현재 권한을 처리·저장 시점에 재확인 유효하지 않은 이전 실행의 저장을 거절

outbox는 아직 전달해야 할 작업 기록, claim은 실행권 획득, generation은 실행의 유효성을 구별하는 번호입니다.
중복 가능성을 전제로 확인하는 구조이며, 모든 외부 동작이 정확히 한 번 실행된다는 보장은 하지 않습니다.

02. 수집한 코드는 읽을 자료로만 다룹니다

GitHub App에서 사용자가 허용한 저장소·폴더를 읽고, 선택한 버전의 commit SHA를 고정해 수집합니다.
파일·주석·문서에 적힌 명령이나 업로드된 분석 설정을 실행 지시로 사용하지 않습니다.
고객 코드의 패키지 설치·빌드·테스트·실행도 하지 않습니다.


격리 환경과 외부 조회의 경계

작업마다 네트워크가 차단된 임시 Vercel Sandbox를 만들고, 고정한 Semgrep·Gitleaks와 자체 분석 도구를 실행합니다.
이 환경에서 코드 규칙 분석, 비밀정보 탐지·마스킹, 지원 의존성 목록 추출을 수행합니다.
공개 취약점 조회는 Sandbox 밖의 서버가 OSV에 패키지 이름·버전·생태계를 보내 처리합니다.

사용자 요청은 자신의 세션 권한으로 처리하고, 서버의 작업 공간 확인과 PostgreSQL RLS를 함께 적용했습니다.
관리 자격 증명은 수집·Workflow·정리 경로에 한정하고, 수집 자료는 private Storage에 보관합니다.
마스킹을 적용해도 모든 비밀정보를 완전히 제거했다고 보증하지는 않습니다.


자체 분석기가 확인하는 범위

지원하는 TypeScript Route Handler의 함수·파일 간 SQL·셸 흐름과, 사용자가 선언한 객체 소유권 조건을 정적으로 분석합니다.
일부 서버 컴포넌트에서는 인증 호출, 조회 조건과 필드, Client로 전달하는 값을 기록합니다.
이 데이터 전달 기록 자체를 취약점 후보나 안전 판정으로 바꾸지는 않습니다.
자체 분석기의 선택 범위는 최대 64파일·합계 1 MiB·파일당 256 KiB이며, GitHub 수집 한도와 별개입니다.
지원하지 않는 호출·동적 흐름, Client 본문과 실제 DB의 RLS 집행은 확인하지 못한 범위로 남깁니다.

03. AI 후보에도 근거를 요구합니다

규칙이 놓치는 문맥을 살펴보기 위해, 별도로 동의한 점검에서 AI가 코드의 위험 후보를 독립적으로 찾도록 했습니다.
규칙 결과가 0건이어도 시작할 수 있으며, 읽기·검색 도구만 제공하고 코드 실행·수정·임의 네트워크 도구는 제공하지 않습니다.


발견 → 반증 → 인용 대조

  1. 조사: 같은 대화에서 저장소와 신뢰 경계를 파악하고 가설을 조사해 후보·공격 조건·영향·근거를 구성합니다.
  2. 반증: 후보가 있으면 별도 대화 문맥에서 관련 코드를 다시 읽고, 후보를 유지하거나 제외할 근거를 검토합니다.
  3. 대조: 서버가 파일·줄 좌표로 인용 원문을 복원하고, 해당 단계에서 실제 제공한 코드와 일치하는지 검사합니다.
  4. 기록: 유지한 후보와 미점검 범위를 규칙 결과와 분리해 저장합니다.
    근거가 부족한 후보는 표시할 후보에 넣지 않습니다.

OpenAI Responses의 구조화 출력과 store: false를 사용하고, 요청·시간·읽기 분량에 상한을 뒀습니다.
거절·시간 초과·형식 오류는 정상적인 0건 결과로 바꾸지 않습니다.
store: false 설정과 제공자의 데이터 보관 정책은 별개이며, 인용 일치도 추론의 정확성을 증명하지는 않습니다.

AI가 읽은 범위는 서버의 파일·줄 제공 기록으로 집계합니다.
읽지 않은 파일, 일부만 읽은 파일, 문맥에서 제외한 파일을 구별하고, AI 후보가 스캐너의 출처·위험도·처리 상태를 덮어쓰지 않도록 했습니다.
수정 코드 예시는 검토를 돕는 제안이며, 자동 적용하거나 실행해 효과를 검증한 수정본은 아닙니다.

04. 결과가 줄었다는 이유만으로 해결이라고 하지 않습니다

새 점검에서 항목이 사라져도, 파일이 제외됐거나 규칙이 바뀐 결과일 수 있습니다.
재점검은 엔진·규칙 버전과 해당 파일의 점검 완료 범위를 대조한 뒤, 재탐지 / 미검출 / 판단 보류로 구분합니다.
실시간으로 취약점 정보가 바뀌는 의존성 결과와 AI 후보에는 같은 방식의 자동 해결 판정을 적용하지 않습니다.


추적과 부분 완료

비밀정보는 원문 대신 프로젝트별 HMAC 식별값을 사용해 같은 파일·규칙·값을 추적합니다.
줄이 이동해도 처리 기록을 이어 가지만, 파일 이동·식별 키 변경·이전 식별 방식의 결과를 임의로 연결하지 않습니다.
식별할 수 있는 파일 파싱 오류가 발생하면 정상 파일의 검증된 근거는 보존하고, 실패 범위와 부분 완료 상태를 함께 보여줍니다.

발견 항목의 담당자·검토 상태·위험 수용 기록은 분석 결과와 구별해 저장합니다.
사용자가 항목을 어떻게 다루기로 했는지와, 분석에서 무엇을 관측했는지를 각각 확인할 수 있습니다.

05. 분석이 끝난 뒤의 정리도 작업에 포함했습니다

정리 요청을 보냈다는 사실만으로 삭제 완료를 표시하면, 실제 처리 상태와 화면이 달라질 수 있습니다.
Sandbox 정지 확인 → 원본 객체 삭제·부재 확인 → 종료 기록 → 사용 예약 반환 순서로 정리합니다.
실패한 정리는 상태를 남겨 재조정하고, AI 임시 문맥도 종료·취소·만료에 따라 정리합니다.

이 확인은 서비스와 저장소 API에서 관측한 상태를 뜻합니다.
물리 저장 장치의 완전 삭제 감사나 모든 장애에서의 즉시 복구 보장은 아닙니다.
