# teum.(틈)

teum은 GitHub에 올린 코드에서 **배포 전에 확인할 보안 위험을 찾는 서비스**입니다.<br>
근거를 읽고, 수정한 코드를 다시 확인할 수 있습니다.<br>
위험한 코드 패턴, 노출된 키·토큰, 외부 패키지의 알려진 취약점을 기본으로 점검합니다.<br>
선택한 경우 AI가 관련 코드를 읽으며 위험 후보와 방어 조건을 추가로 검토합니다.<br>
결과마다 어디를 확인했고 무엇을 확인하지 못했는지 함께 보여줍니다.<br><br>

기획 · 제품 UI · 웹/서버 구현 · 분석 파이프라인 · 검증과 배포

## 01. 위험을 찾은 다음, 무엇을 해야 할까요?

작동하는 서비스를 만들었다고 해서, 그 안의 권한 처리와 비밀정보까지 확인한 것은 아닙니다.<br>
점검 도구가 위험을 알려줘도 파일 이름과 경고 목록만으로는 무엇부터 고쳐야 할지 판단하기 어렵습니다.<br><br>

teum에서는 **발견 → 근거 확인 → 검토 기록 → 수정본 재점검**을 한 작업 공간에서 진행합니다.<br>
결과 목록 옆에서 코드와 설명을 읽고, 수정 방향을 검토한 뒤 같은 항목이 다시 발견되는지 확인할 수 있습니다.<br><br>

![공개 샘플의 규칙 분석 결과. 발견 목록과 선택한 항목의 코드 근거를 같은 화면에서 검토합니다.](/Users/domado/Documents/GitHub/teum_public/assets/screenshots/rule-review.jpg)

*공개 샘플 화면 · 2026-10-14 캡처.<br>
화면의 발견 건수는 제품 설명을 위한 예시입니다.*<br>

<br>

### 한 항목에서 확인할 수 있는 것

| 확인할 질문 | 화면에서 볼 수 있는 정보 |
|---|---|
| 어디에 문제가 있나요?<br> | 파일·줄 위치와 마스킹된 코드 근거 |
| 왜 확인해야 하나요?<br> | 위험이 생기는 조건, 영향, 먼저 확인할 일 |
| 어떻게 고치나요?<br> | 수정 방향과, AI 후보의 경우 검토용 코드 변경 예시 |
| 어디까지 검토했나요?<br> | 담당 여부, 처리 상태, 위험 수용 기록 |
| 고친 뒤에는 달라졌나요?<br> | 비교 조건을 확인한 재점검 결과와 HTML/JSON 리포트 |

처리 상태를 바꾸는 것과 실제로 다시 점검하는 것은 구분합니다.<br>
담당자가 검토를 마쳤다는 기록만으로 이전 분석 결과를 ‘해결’로 바꾸지 않습니다.<br><br>

## 02. 저장소 연결부터, 수정 후 확인까지

*[가로 SVG](/Users/domado/Documents/GitHub/teum_public/assets/diagrams/review-flow.svg) · [모바일 SVG](/Users/domado/Documents/GitHub/teum_public/assets/diagrams/review-flow-mobile.svg) · 움직임은 단계의 연결을 설명하며 실제 실행 시간이나 진행률을 나타내지 않습니다.*<br><br>

1. **확인할 코드를 정합니다.**<br>
   GitHub App에 허용한 저장소에서 브랜치와 폴더를 선택합니다.<br>
   수집할 파일을 확인하고, 특정 커밋의 코드로 입력을 고정합니다.<br>
2. **점검을 시작합니다.**<br>
   기본 보안 점검을 실행합니다.<br>
   AI 검토는 별도 선택과 코드 전송 동의가 있을 때 추가합니다.<br>
3. **근거를 읽고 기록합니다.**<br>
   규칙 분석과 AI 후보를 구분해 보고, 성립 조건과 확인하지 못한 부분을 살펴봅니다.<br>
4. **수정한 코드를 다시 확인합니다.**<br>
   새 커밋으로 재점검하고, 비교 가능한 항목의 변화를 확인합니다.<br>
   결과는 HTML/JSON으로 내보낼 수 있습니다.<br>

<br>

### 기본 점검과 AI 검토가 맡는 일

| 구분 | 확인하는 내용 | 결과를 읽는 기준 |
|---|---|---|
| 정적 규칙 분석 | JavaScript·TypeScript·Python의 위험한 코드 패턴과 지원하는 입력 흐름 | 규칙과 해당 코드 근거를 함께 확인 |
| 비밀정보 탐지 | 코드에 들어간 키·토큰 등 비밀정보의 형태 | 값은 마스킹하고 발견 위치를 제공 |
| 의존성 대조 | 지원하는 잠금 파일·고정 버전 목록을 OSV 공개 취약점 정보와 대조 | 해당 패키지의 실제 실행·공격 가능성은 별도 확인 |
| 자체 코드 분석 | 지원하는 TypeScript의 함수·파일 간 SQL·셸 흐름, 선언한 객체 소유권 조건, 서버에서 Client로 전달하는 데이터 | 분석별 지원 범위와 미확인 조건을 표시하며, 데이터 전달 기록 자체를 취약점으로 판정하지 않음 |
| 선택 AI 검토 | 관련 코드를 읽고 독립적인 위험 후보와 방어 근거를 검토 | 규칙 결과와 별도 표시하며, 사람이 검토할 후보로 제공 |

현재 새 점검 입력은 **GitHub 연결**입니다.<br>
직접 점검은 등록된 계정에서 이용하며, 공개 샘플은 로그인 없이 볼 수 있습니다.<br>
직접 ZIP 업로드, 임의 웹사이트 점검, 자동 PR 점검은 제공하지 않습니다.<br><br>

## 03. 짧은 웹 요청과 긴 분석 작업을 나눴습니다

화면에서 점검을 시작하는 요청은 짧게 끝나지만, 코드 수집과 분석·정리는 그 뒤에도 이어져야 합니다.<br>
Next.js는 화면과 API를 처리하고, Workflow는 후속 작업을 이어 갑니다.<br>
Sandbox에서는 격리된 정적 분석을 실행합니다.<br><br>

![Next.js와 Supabase, Workflow, 네트워크가 차단된 Sandbox, 외부 OSV와 선택 OpenAI 검토의 경계를 보여주는 시스템 아키텍처](/Users/domado/Documents/GitHub/teum_public/assets/diagrams/architecture.svg)

*[SVG 크게 보기](/Users/domado/Documents/GitHub/teum_public/assets/diagrams/architecture.svg) · 세부 API와 내부 식별자를 생략한 구현 구조입니다.*<br><br>

| 구성 | 사용 기술 | 맡은 역할 |
|---|---|---|
| 웹 화면·API | Next.js App Router · React · TypeScript | 공개 홈과 작업 공간, 입력 검증과 권한 검사 |
| 계정·데이터 | Supabase Auth · PostgreSQL · private Storage | 로그인, 작업과 결과 기록, 비공개 입력 보관 |
| 작업 실행 | Vercel Workflow | 코드 수집, 분석 단계, 재시도와 정리 |
| 격리 분석 | Vercel Sandbox · Semgrep CE · Gitleaks · 자체 분석기 | 코드·비밀정보 분석, 의존성 추출, 자체 코드 흐름 분석 |
| 외부 대조·검토 | OSV · OpenAI Responses API | 공개 패키지 취약점 대조, 동의한 코드의 선택 AI 검토 |
| 화면 표현 | CSS · GSAP · Shiki | 브랜드 모션, 코드 구문 강조와 변경 비교 |

Sandbox 안에서는 네트워크를 차단하고 고객 코드의 설치·빌드·실행을 하지 않습니다.<br>
OSV에는 공개 패키지 이름·버전·생태계를 보내며, AI를 선택하면 동의한 범위의 코드 문맥을 별도로 보냅니다.<br>
두 외부 호출은 Sandbox 밖의 서버 단계에서 수행합니다.<br><br>

GitHub 수집과 분석은 별도 Workflow로 실행합니다.<br>
수집한 입력을 저장한 뒤, **규칙 분석·의존성 추출 → OSV 조회 → 자체 코드 흐름 분석 → 결과 저장 → 선택 AI 검토 → 정리** 순서로 진행합니다.<br>
GitHub 파일 수집은 최대 8개, OSV 조회는 최대 4개 요청을 병렬로 처리합니다.<br>
Sandbox 분석과 AI 검토를 동시에 실행하는 구조는 아닙니다.<br><br>

조건이 같은 이전 결과는 검증 후 캐시에서 재사용할 수 있습니다.<br>
재사용하더라도 입력 준비와 권한 확인이 필요하며, OSV 취약점 정보는 다시 조회합니다.<br>

## 04. 구현에서 중요했던 네 가지 판단

### 1. ‘발견 0건’과 ‘확인하지 못함’을 구분하기

분석이 실패했는데 빈 목록을 보여주면 사용자는 문제가 없다고 받아들일 수 있습니다.<br>
완료·부분 완료·실패·미지원·취소를 구분하고, 일부 파일에서 실패해도 정상 파일의 검증된 근거와 미완료 범위를 함께 남겼습니다.<br>

<br>

### 2. AI가 말한 내용을 코드와 다시 대조하기

AI 검토는 같은 대화에서 저장소를 이해하고 후보를 조사한 뒤, 후보가 있으면 별도 대화에서 방어 근거와 반례를 살펴봅니다.<br>
서버는 인용한 파일·줄·내용이 실제 제공한 코드와 일치하는지 검사하고, 읽은 범위를 기록합니다.<br>
AI의 제안은 규칙 결과와 별도로 저장하며, 수정 예시는 자동 적용하거나 병합하지 않습니다.<br><br>

![공개 샘플의 AI 후보. 먼저 확인할 일과 코드 인용 근거를 보여주고 실행 검증 여부를 구분합니다.](/Users/domado/Documents/GitHub/teum_public/assets/screenshots/ai-review.jpg)

*AI 검토 화면도 고정 샘플입니다.<br>
실제 모델의 성능을 입증하는 자료가 아닙니다.*<br>

<br>

### 3. 요청이 끊겨도 작업을 추적할 수 있게 만들기

작업과 실행 요청을 DB에 함께 남기고, Workflow가 실행 상태를 이어받도록 했습니다.<br>
재시도나 중복 전달이 생겨도 현재 작업의 실행권과 상태를 확인하며, 취소·삭제된 작업의 늦은 결과는 저장하지 않도록 검사합니다.<br>
분석 환경 종료와 원본 자료 삭제도 각각 확인한 뒤 기록합니다.<br>

<br>

### 4. 재점검을 단순한 숫자 비교로 끝내지 않기

발견 건수가 줄어도 규칙이 달라졌거나 해당 파일을 읽지 못했다면 수정 효과라고 단정할 수 없습니다.<br>
엔진·규칙·파일의 점검 완료 범위를 대조해 비교하고, 조건이 맞지 않으면 판단을 보류합니다.<br>
AI 후보의 자동 재점검 비교는 현재 지원 범위에서 제외했습니다.<br><br>

# teum. — 구현에서 중요하게 다룬 것

코드에서 위험을 찾는 기능을 만들면서, 결과를 어떤 근거로 보여줄지도 함께 설계했습니다.<br>
아래는 2026년 10월 30일 비공개 저장소의 최신 `main`과 대조한 구현 구조와 그 선택의 이유입니다.<br>
[서비스 소개](/Users/domado/Documents/GitHub/teum_public/README.md) · [검증과 한계](/Users/domado/Documents/GitHub/teum_public/docs/VALIDATION.md) · [서비스 둘러보기](https://teum.today)

<br>
<br>

## 01. 요청 처리와 분석 실행을 나눴습니다

분석은 화면 요청보다 오래 걸리고, 사용자가 브라우저를 닫거나 같은 요청을 다시 보낼 수도 있습니다.<br>
Next.js API는 인증·입력·권한을 확인해 작업을 준비하고, Vercel Workflow가 실제 분석을 이어 갑니다.<br>
서버 코드는 Route → 입력 검증 → Service → Repository/RPC로 나눴습니다.<br><br>

GitHub 수집용 Workflow가 고정 커밋의 파일을 모아 private Storage에 저장합니다.<br>
준비된 입력으로 분석용 Workflow를 시작하면 **규칙 분석·의존성 추출 → OSV 조회 → 자체 코드 분석 → 결과 저장 → Sandbox 정지 → 선택 AI 검토와 후보 저장 → 원본 정리** 순서로 실행합니다.<br>
파일 수집은 최대 8개, OSV 조회는 최대 4개 요청을 병렬로 처리합니다.<br>
두 병렬 처리는 각각의 단계 안에서 이루어집니다.<br><br>

입력·엔진·규칙·분석 설정 등의 조건이 같은 결과는 검증 후 캐시에서 재사용할 수 있습니다.<br>
재사용 시에도 입력 준비와 현재 권한을 확인하며, OSV 조회 결과를 그대로 재사용하지 않습니다.<br>
AI에 코드를 보낼 때는 비밀정보를 다시 점검하므로, 이전 정적 분석 결과만으로 AI 문맥을 만들지 않습니다.<br>

<br>

### 작업 시작과 결과 저장의 기준

| 문제 | 구현 선택 | 얻은 동작 |
|---|---|---|
| DB 저장과 외부 Workflow 시작을 하나의 트랜잭션으로 묶을 수 없음 | 실행 기록과 outbox를 함께 저장 | 시작 요청이 실패해도 재조정할 대상을 DB에 남김 |
| 같은 작업이 중복 전달될 수 있음 | DB의 claim과 lease로 실행권 확인 | 현재 실행권을 얻은 작업이 단계를 진행 |
| 취소·권한 철회 이후 이전 응답이 도착할 수 있음 | 작업 generation과 현재 권한을 처리·저장 시점에 재확인 | 유효하지 않은 이전 실행의 저장을 거절 |

outbox는 아직 전달해야 할 작업 기록, claim은 실행권 획득, generation은 실행의 유효성을 구별하는 번호입니다.<br>
중복 가능성을 전제로 확인하는 구조이며, 모든 외부 동작이 정확히 한 번 실행된다는 보장은 하지 않습니다.<br><br>

## 02. 수집한 코드는 읽을 자료로만 다룹니다

GitHub App에서 사용자가 허용한 저장소·폴더를 읽고, 선택한 버전의 commit SHA를 고정해 수집합니다.<br>
파일·주석·문서에 적힌 명령이나 업로드된 분석 설정을 실행 지시로 사용하지 않습니다.<br>
고객 코드의 패키지 설치·빌드·테스트·실행도 하지 않습니다.<br>

<br>

### 격리 환경과 외부 조회의 경계

작업마다 네트워크가 차단된 임시 Vercel Sandbox를 만들고, 고정한 Semgrep·Gitleaks와 자체 분석 도구를 실행합니다.<br>
이 환경에서 코드 규칙 분석, 비밀정보 탐지·마스킹, 지원 의존성 목록 추출을 수행합니다.<br>
공개 취약점 조회는 Sandbox 밖의 서버가 OSV에 패키지 이름·버전·생태계를 보내 처리합니다.<br><br>

사용자 요청은 자신의 세션 권한으로 처리하고, 서버의 작업 공간 확인과 PostgreSQL RLS를 함께 적용했습니다.<br>
관리 자격 증명은 수집·Workflow·정리 경로에 한정하고, 수집 자료는 private Storage에 보관합니다.<br>
마스킹을 적용해도 모든 비밀정보를 완전히 제거했다고 보증하지는 않습니다.<br>

<br>

### 자체 분석기가 확인하는 범위

지원하는 TypeScript Route Handler의 함수·파일 간 SQL·셸 흐름과, 사용자가 선언한 객체 소유권 조건을 정적으로 분석합니다.<br>
일부 서버 컴포넌트에서는 인증 호출, 조회 조건과 필드, Client로 전달하는 값을 기록합니다.<br>
이 데이터 전달 기록 자체를 취약점 후보나 안전 판정으로 바꾸지는 않습니다.<br>
자체 분석기의 선택 범위는 최대 64파일·합계 1 MiB·파일당 256 KiB이며, GitHub 수집 한도와 별개입니다.<br>
지원하지 않는 호출·동적 흐름, Client 본문과 실제 DB의 RLS 집행은 확인하지 못한 범위로 남깁니다.<br><br>

## 03. AI 후보에도 근거를 요구합니다

규칙이 놓치는 문맥을 살펴보기 위해, 별도로 동의한 점검에서 AI가 코드의 위험 후보를 독립적으로 찾도록 했습니다.<br>
규칙 결과가 0건이어도 시작할 수 있으며, 읽기·검색 도구만 제공하고 코드 실행·수정·임의 네트워크 도구는 제공하지 않습니다.<br>

<br>

### 발견 → 반증 → 인용 대조

1. **조사:** 같은 대화에서 저장소와 신뢰 경계를 파악하고 가설을 조사해 후보·공격 조건·영향·근거를 구성합니다.<br>
2. **반증:** 후보가 있으면 별도 대화 문맥에서 관련 코드를 다시 읽고, 후보를 유지하거나 제외할 근거를 검토합니다.<br>
3. **대조:** 서버가 파일·줄 좌표로 인용 원문을 복원하고, 해당 단계에서 실제 제공한 코드와 일치하는지 검사합니다.<br>
4. **기록:** 유지한 후보와 미점검 범위를 규칙 결과와 분리해 저장합니다.<br>
   근거가 부족한 후보는 표시할 후보에 넣지 않습니다.<br><br>

OpenAI Responses의 구조화 출력과 `store: false`를 사용하고, 요청·시간·읽기 분량에 상한을 뒀습니다.<br>
거절·시간 초과·형식 오류는 정상적인 0건 결과로 바꾸지 않습니다.<br>
`store: false` 설정과 제공자의 데이터 보관 정책은 별개이며, 인용 일치도 추론의 정확성을 증명하지는 않습니다.<br><br>

AI가 읽은 범위는 서버의 파일·줄 제공 기록으로 집계합니다.<br>
읽지 않은 파일, 일부만 읽은 파일, 문맥에서 제외한 파일을 구별하고, AI 후보가 스캐너의 출처·위험도·처리 상태를 덮어쓰지 않도록 했습니다.<br>
수정 코드 예시는 검토를 돕는 제안이며, 자동 적용하거나 실행해 효과를 검증한 수정본은 아닙니다.<br><br>

## 04. 결과가 줄었다는 이유만으로 해결이라고 하지 않습니다

새 점검에서 항목이 사라져도, 파일이 제외됐거나 규칙이 바뀐 결과일 수 있습니다.<br>
재점검은 엔진·규칙 버전과 해당 파일의 점검 완료 범위를 대조한 뒤, **재탐지 / 미검출 / 판단 보류**로 구분합니다.<br>
실시간으로 취약점 정보가 바뀌는 의존성 결과와 AI 후보에는 같은 방식의 자동 해결 판정을 적용하지 않습니다.<br>

<br>

### 추적과 부분 완료

비밀정보는 원문 대신 프로젝트별 HMAC 식별값을 사용해 같은 파일·규칙·값을 추적합니다.<br>
줄이 이동해도 처리 기록을 이어 가지만, 파일 이동·식별 키 변경·이전 식별 방식의 결과를 임의로 연결하지 않습니다.<br>
식별할 수 있는 파일 파싱 오류가 발생하면 정상 파일의 검증된 근거는 보존하고, 실패 범위와 부분 완료 상태를 함께 보여줍니다.<br><br>

발견 항목의 담당자·검토 상태·위험 수용 기록은 분석 결과와 구별해 저장합니다.<br>
사용자가 항목을 어떻게 다루기로 했는지와, 분석에서 무엇을 관측했는지를 각각 확인할 수 있습니다.<br><br>

## 05. 분석이 끝난 뒤의 정리도 작업에 포함했습니다

정리 요청을 보냈다는 사실만으로 삭제 완료를 표시하면, 실제 처리 상태와 화면이 달라질 수 있습니다.<br>
**Sandbox 정지 확인 → 원본 객체 삭제·부재 확인 → 종료 기록 → 사용 예약 반환** 순서로 정리합니다.<br>
실패한 정리는 상태를 남겨 재조정하고, AI 임시 문맥도 종료·취소·만료에 따라 정리합니다.<br><br>

이 확인은 서비스와 저장소 API에서 관측한 상태를 뜻합니다.<br>

## 03. AI 검토는 구현과 품질 평가를 구별합니다
